这次关闭发生在 HTTP 交付后约 26ms，不是 5 分钟 TTL 到期。DSH 持久化记录表明已执行批次的两条结果都已生成；没有捕获出站 HTTP 原始正文，因此不声称独立验证了网络上传输的全部字段。不过 `action=fail` 已足以解释随后无法找到 Run 的直接原因。日志没有记录迟到通知的 call/exec 身份，不能进一步区分它是真正的第三个独立工具，还是使用不同 call ID 的重复通知；当前 paused 分支仅比较 upstream call ID，而 running 分支也比较 exec ID，这是后续必须覆盖的边界，不能把第三个独立工具当成已证实事实。

## 观察后验收项

以下是由旧样本提出的验收要求；目前实现和离线验证已完成，修复后的真实请求验证仍待进行：

1. 将已交付批次与尚未交付工具分开保存；已交付 ID、参数与结果集合不可因后续通知变化。
2. 新工具进入有界待派发队列；旧批次的完整结果仍只回写一次，继续同一上游 Run，下一次 HTTP 响应派发待处理工具。此方案须先用协议 fixture 验证，不视作已完成设计认证。
3. 覆盖交付前后到达、多工具、重复通知、同 exec 的不同 call ID、分片、参数更新、连续多轮，以及取消/替换/TTL/队列上限。验证不丢工具、不重复执行、不跨 lane、不额外创建 Run，也不提前宣告完成。
4. 增加可区分的失效原因及脱敏诊断；继续严格拒绝真正缺失、重复、过期的工具结果，不把 409 改为自动重试。
5. 修复经离线测试和实际请求验证后，再考虑缩短收集窗口。单纯增大窗口只能推迟下一次迟到，缩小窗口则扩大当前失败机会。

已经关闭的 Run 不能靠重复提交同一批工具结果恢复；不要自动重放已执行工具来掩盖错误。
